    # The Three Parts of an S3 Object:
        An S3 object can be understood through three important parts:

            1. Data
            2. Metadata
            3. Key

        Together:
            - Data is the actual content.
            - Metadata describes the object.
            - Key identifies the object inside the bucket.


    # 1. Data:
        Data means the actual bytes stored in the object.

        Examples:
            - Text file contents
            - Image pixels
            - PDF content
            - Video data
            - Backup files
            - ZIP archives
            - Application assets

        S3 is content-agnostic.

        This means:
            - S3 does not care whether the object is an image, video, PDF,
              backup, or another file type.
            - It stores the object as bytes.


    # 2. Metadata:
        Metadata means:

            "Information about the object."

        Metadata helps describe:
            - What type of object it is.
            - How large it is.
            - When it was modified.
            - Other object-related information.

        S3 metadata can include:
            - System-defined metadata
            - User-defined metadata


    # 3. Key:
        The key is the unique identifier of an object inside an S3 bucket.

        Example:

            invoices/2026/jan.pdf

        Here:
            - Bucket name identifies the bucket.
            - invoices/2026/jan.pdf identifies the object.

        Important:
            - The complete string is the object key.
            - Slash characters are part of the key.
            - They are commonly used as prefixes for logical organization.


    # Example Object:
        Bucket:
            company-documents

        Object Key:
            resumes/rizwan/resume.pdf

        Data:
            Actual PDF contents

        Metadata:
            Content type, size, last modified information, etc.

        Together:
            Bucket + Key
                --> Identifies the stored object.


    # Object Metadata:
        S3 object metadata is commonly divided into:

            1. System Metadata
            2. User-Defined Metadata


    # System Metadata:
        System metadata is metadata managed or recognized by Amazon S3.

        Common examples include:

            Content-Type
                --> MIME type of the object.

            Content-Length
                --> Size of the object in bytes.

            Last-Modified
                --> Time when the object was last modified.

            ETag
                --> Identifier associated with the stored object version.

        Example Content-Type values:

            image/jpeg
            image/png
            application/pdf
            text/html


    # Content-Type Matters:
        Content-Type tells browsers and applications how the object should be handled.

        Example:

            Correct:
                Content-Type: image/jpeg

            Result:
                --> Browser can display the image.

        If Content-Type is incorrect:
            - The browser may download the file instead.
            - The browser may display it incorrectly.


    # About ETag:
        ETag is an identifier returned by S3 for an object.

        Important:
            - It is often useful for change detection.
            - For some simple uploads it may match an MD5-style value.
            - You should not assume every ETag is always a direct MD5 checksum,
              especially with multipart uploads or certain encryption methods.


    # User-Defined Metadata:
        You can add your own metadata to an S3 object.

        User-defined metadata is stored as custom key-value information.

        AWS uses headers beginning with:

            x-amz-meta-

        Example:

            x-amz-meta-photographer: Ali
            x-amz-meta-client: Company-A
            x-amz-meta-department: HR

        Useful for:
            - Classification
            - Tracking
            - Application-specific information
            - Business context


    # Metadata Can Be Read Without Downloading the Object Body:
        Applications can retrieve object metadata without downloading
        the complete object body.

        Example operation:
            --> HEAD request

        Benefit:
            - Check object information quickly.
            - Avoid unnecessary data transfer.


    # User-Defined Metadata vs Object Tags:
        These are related but different concepts.

        # User-Defined Metadata:
            - Stored as object metadata.
            - Commonly added when the object is uploaded.
            - Uses x-amz-meta-* headers.
            - Changing user-defined metadata generally requires copying or
              replacing the object with new metadata.

        # Object Tags:
            - Separate key-value pairs attached to the object.
            - Can be added or changed independently.
            - Useful for:
                - Lifecycle rules
                - Access control
                - Cost allocation
                - Classification
                - Automation

        Example Tags:

            Environment = Production
            Department = HR
            Project = ERP


    # S3 Durability:
        Durability answers:

            "Will my data still exist?"

        Amazon S3 Standard is designed for:

            99.999999999% durability

        This is called:

            Eleven Nines of Durability


    # What Eleven Nines Means:
        99.999999999% durability represents an extremely low probability
        of object loss.

        Example concept:

            If you stored 10,000,000 objects:

                Expected statistical object loss
                    --> About one object every 10,000 years

        Important:
            - This is a statistical durability design target.
            - It does not mean one object will literally be lost on a schedule.


    # How S3 Achieves High Durability:
        For S3 Standard:

            - Objects are redundantly stored across multiple devices.
            - Data is stored across multiple Availability Zones.
            - These Availability Zones are within the same AWS Region.

        Important:
            - S3 Standard does not automatically replicate your object to another
              AWS Region for durability.
            - Cross-Region Replication must be configured separately if required.


    # Built-In Durability:
        For normal S3 Standard storage:

            - You do not manually design device-level replication.
            - AWS manages the underlying redundancy automatically.

        Result:
            - High durability is built into the service.


    # Durability vs Availability:
        These are different concepts.

        # Durability:
            Question:
                "Does my data still exist?"

            S3 Standard Design:
                --> 99.999999999% durability

        # Availability:
            Question:
                "Can I access the service and object right now?"

            S3 Standard Design:
                --> 99.99% availability


    # Understanding 99.99% Availability:
        99.99% availability corresponds to approximately:

            Less than 53 minutes of potential unavailability per year

        This is only a mathematical interpretation.

        Important:
            - Actual service availability varies over time.
            - Availability does not mean the data is lost.
            - An object can still exist even during a temporary access problem.


    # Simple Durability vs Availability Example:
        Scenario:
            Your object still exists safely in S3.

        But:
            A temporary network or service issue prevents access.

        Result:
            Durability:
                --> Data still exists.

            Availability:
                --> Temporarily unavailable.


    # Pre-Signed URLs:
        A pre-signed URL is a time-limited URL that grants temporary access
        to a specific S3 operation.

        It contains:
            - S3 object or request information
            - Cryptographic signature
            - Expiration information


    # Why Use Pre-Signed URLs?
        Suppose:

            - Your S3 bucket is private.
            - Your object is private.
            - A client needs temporary access to one file.

        Bad Approach:
            --> Make the entire bucket public.

        Better Approach:
            --> Generate a pre-signed URL for that specific object.


    # Pre-Signed URL Flow:
        1. Object stays private.

        2. Application generates a pre-signed URL.

        3. URL includes authorization information.

        4. User receives the temporary link.

        5. User accesses the object before expiration.

        6. After expiration:
            --> The URL no longer works.


    # Example Pre-Signed URL Use Case:
        Scenario:
            Application stores invoices in a private S3 bucket.

        Requirement:
            Customer needs to download one invoice.

        Solution:
            - Generate a pre-signed URL valid for 24 hours.
            - Email the URL to the customer.
            - Bucket stays private.


    # Pre-Signed URLs Can Support Different Operations:
        Depending on how the URL is generated and what the creator is allowed to do,
        a pre-signed URL can be used for operations such as:

            - Downloading an object
            - Uploading an object

        Important:
            - The URL cannot grant permissions beyond those available to the
              identity that generated it.


    # Use Case 1 - Static Website Hosting:
        S3 can host static website content.

        Static content can include:

            - HTML
            - CSS
            - JavaScript
            - Images
            - Fonts
            - Documents

        No application server is required for purely static content.


    # Static Website Hosting Flow:
        1. Create an S3 bucket.
        2. Upload website files.
        3. Enable static website hosting.
        4. Configure index document.
        5. Configure access appropriately.
        6. Use the S3 website endpoint or place CloudFront in front of S3.


    # Important About S3 Website Endpoints:
        Native S3 website endpoints:

            - Are intended for static website hosting.
            - Use HTTP.

        For production HTTPS delivery:

            Better approach:
                --> Use Amazon CloudFront in front of S3.


    # S3 + CloudFront:
        CloudFront is AWS's content delivery network.

        Benefits:
            - HTTPS support
            - Global edge delivery
            - Lower latency
            - Caching
            - Better performance for global users

        Common Use Cases:
            - Marketing websites
            - Portfolios
            - Documentation
            - Landing pages
            - Static application front ends


    # Use Case 2 - Backup and Disaster Recovery:
        S3 is commonly used as a backup destination.

        Examples:
            - Application archives
            - Database exports
            - Log archives
            - File backups
            - Backup copies
            - Disaster recovery data


    # AWS Service Backups and S3:
        AWS services such as EBS and RDS use S3-backed infrastructure for
        snapshot storage internally.

        Important:
            - EBS snapshots and RDS snapshots are managed through their own services.
            - They are not normal user-visible objects inside your S3 buckets.


    # Cross-Region Replication:
        S3 can replicate objects to another AWS Region when configured.

        This is called:

            Cross-Region Replication (CRR)

        Benefits:
            - Geographic redundancy
            - Compliance
            - Disaster recovery
            - Regional data-copy requirements

        Important:
            - CRR is not automatically enabled.
            - It must be configured.


    # Use Case 3 - Data Lakes:
        S3 is widely used as the storage foundation for data lakes.

        A data lake is:

            A central repository for storing large amounts of structured,
            semi-structured, and unstructured data.

        Examples:
            - CSV
            - JSON
            - Parquet
            - Logs
            - Images
            - Videos
            - Application events


    # Data Lake Analytics:
        Data stored in S3 can be analyzed using services such as:

            - Amazon Athena
            - Amazon EMR
            - Amazon Redshift Spectrum
            - AWS Glue

        Example:

            Raw Data
                --> Amazon S3
                --> Query / Transform / Analyze


    # Use Case 4 - Application File Storage:
        Applications can store user-uploaded files in S3 instead of local server disks.

        Examples:
            - Profile pictures
            - Documents
            - Videos
            - Attachments
            - Reports
            - Product images


    # Why Store Application Files in S3?
        Suppose an application runs on EC2.

        If files are stored only on the EC2 local disk:

            - Instance replacement can complicate file persistence.
            - Scaling to multiple servers becomes harder.

        Better pattern:

            User Upload
                --> S3

            EC2 / Lambda / Other Compute
                --> Access Same S3 Objects

        Principle:
            --> Separate compute from storage.


    # Benefits of Separating Compute and Storage:
        1. EC2 instances can be replaced independently.

        2. Multiple application servers can access the same objects.

        3. Storage scales separately from compute.

        4. Application architecture becomes easier to scale.

        5. Files are not tied to one server's local disk.


    # Use Case 5 - Software and Media Distribution:
        S3 can store downloadable content such as:

            - Application installers
            - Game patches
            - Firmware updates
            - Video files
            - Documents
            - Software packages

        For global delivery:

            S3
                +
            CloudFront
                =
            Global Content Distribution


    # S3 + CloudFront Distribution:
        Example:

            S3 Bucket
                --> Stores software or media

            CloudFront
                --> Caches and distributes content globally

            End Users
                --> Download from nearby edge locations

        Benefit:
            - Lower latency
            - Reduced load on origin
            - Better global performance

    # Security Reminder:
        S3 buckets and objects are private by default unless access is explicitly granted.

        Common access methods include:

            - IAM Policies
            - Bucket Policies
            - Access Points
            - Pre-Signed URLs
            - CloudFront access controls

        Avoid:
            - Making an entire bucket public just to share one private object.


    # Quick Summary:
        1. S3 Object
            --> Data + Metadata + Key.

        2. Data
            --> Actual object bytes.

        3. Metadata
            --> Information about the object.

        4. Key
            --> Unique object identifier inside a bucket.

        5. System Metadata
            --> S3-recognized object information.

        6. User-Defined Metadata
            --> Custom x-amz-meta-* key-value information.

        7. Object Tags
            --> Separate key-value labels used for classification, lifecycle,
                access control, and cost allocation.

        8. S3 Standard Durability
            --> 99.999999999% (eleven nines).

        9. S3 Standard Availability
            --> Designed for 99.99%.

        10. S3 Standard Redundancy
            --> Multiple devices and Availability Zones within a Region.

        11. Pre-Signed URL
            --> Temporary signed access to a private S3 operation.

        12. Static Website
            --> S3 can host HTML, CSS, JavaScript, and assets.

        13. CloudFront
            --> Adds global CDN delivery and HTTPS.

        14. Backups
            --> S3 is widely used for backup and archival data.

        15. Data Lake
            --> S3 can store large-scale raw data for analytics.

        16. Application Storage
            --> Store uploads independently from compute servers.

        17. Distribution
            --> S3 + CloudFront can deliver software and media globally.


    # Lecture Summary:
        "An S3 object consists of data, metadata, and a unique key. Amazon S3
        provides extremely high durability and strong availability for stored
        objects. Pre-signed URLs allow temporary access to private objects without
        making the entire bucket public. S3 is widely used for static websites,
        backups, data lakes, application file storage, and software or media
        distribution, especially when combined with services such as CloudFront."
