

# IAM Roles and Temporary Credentials:
    This lecture explains IAM Roles, how roles are assumed, and how AWS uses
    temporary security credentials instead of permanent credentials for many
    users, applications, and AWS services.


    # What is an IAM Role?
        An IAM Role is an AWS identity that has permissions.

        Unlike an IAM User:
            - A role does not have permanent credentials.
            - A role is assumed when access is needed.
            - The entity assuming the role receives temporary credentials.

        Roles can be used by:
            - IAM users
            - AWS services
            - Applications
            - Users from another AWS account
            - Federated users


    # IAM User vs IAM Role:
        # IAM User:
            - Usually represents one person or application.
            - Can have long-term credentials.
            - Can have a console password.
            - Can have long-term access keys.

        # IAM Role:
            - Is not permanently tied to one person.
            - Is assumed when needed.
            - Provides temporary credentials.
            - Commonly used for AWS services and delegated access.


    # Why Use IAM Roles?
        IAM Roles help avoid storing long-term credentials.

        Benefits:
            1. Temporary credentials expire automatically.
            2. Applications do not need hardcoded access keys.
            3. Permissions can be assigned to AWS services securely.
            4. Roles can provide cross-account access.
            5. Roles support the principle of least privilege.


    # Temporary Security Credentials:
        Temporary security credentials are short-term credentials provided
        when a role is assumed.

        They normally include:

            1. Access Key ID
            2. Secret Access Key
            3. Session Token

        Important:
            - Temporary credentials expire automatically.
            - They are valid only for the role session.
            - New credentials can be obtained when another session is created.


    # Long-Term vs Temporary Credentials:
        # Long-Term Credentials:
            - Commonly associated with IAM users.
            - Remain valid until changed, disabled, or deleted.
            - Require careful storage and rotation.

        # Temporary Credentials:
            - Commonly obtained by assuming an IAM Role.
            - Expire automatically.
            - Reduce the risk of keeping permanent credentials in applications.


    # AWS Security Token Service (STS):
        AWS STS stands for AWS Security Token Service.

        STS provides temporary security credentials.

        A common STS operation is:

            AssumeRole

        AssumeRole:
            - Requests access to an IAM Role.
            - Returns temporary security credentials.
            - Creates a temporary role session.


    # Assume Role:
        To use a role, an authorized identity assumes it.

        Simple flow:

            User / Application / AWS Service
                --> Assumes IAM Role
                --> AWS STS provides temporary credentials
                --> Temporary credentials are used to access AWS resources

        When the session expires:
            - The temporary credentials stop working.


    # Two Important Parts of an IAM Role:
        A role commonly involves two permission decisions:

            1. Trust Policy
            2. Permissions Policy


    # Trust Policy:
        A trust policy defines:

            "Who can assume this role?"

        It identifies the trusted principal.

        Examples:
            - An AWS service
            - An IAM user or role
            - Another AWS account
            - A federated identity provider

        Example:
            An EC2 role can trust:
                --> Amazon EC2 service

        This allows EC2 to assume the role.


    # Permissions Policy:
        A permissions policy defines:

            "What can this role do after it is assumed?"

        Example:
            A role may be allowed to:
                - Read objects from an S3 bucket.

        But it may not be allowed to:
                - Delete objects from the bucket.

        The role receives only the permissions defined by its applicable policies.


    # Trust Policy vs Permissions Policy:
        Trust Policy:
            --> Who can assume the role?

        Permissions Policy:
            --> What can the role do?

        Both are important.

        A role must:
            1. Trust the correct entity.
            2. Have the required permissions.


    # IAM Role for EC2:
        A common use of IAM Roles is giving an EC2 instance access to AWS services.

        Example:
            An application running on EC2 needs to read files from S3.

        Bad Approach:
            - Create an IAM user's access key.
            - Store the access key inside the application.
            - Store the secret key inside the application.

        Better Approach:
            1. Create an IAM Role.
            2. Give the role S3 read permissions.
            3. Allow EC2 to assume the role.
            4. Attach the role to the EC2 instance.
            5. The application uses temporary credentials automatically.


    # EC2 Instance Profile:
        For Amazon EC2, an IAM Role is made available to the instance through
        an instance profile.

        The application on EC2 can obtain temporary credentials without
        hardcoding permanent access keys.

        AWS SDKs and the AWS CLI can normally use these role credentials
        automatically when configured correctly.


    # Simple EC2 Example:
        EC2 Application
            --> IAM Role
            --> Temporary Credentials
            --> Amazon S3

        Role Permission:
            - s3:GetObject

        Result:
            - The application can read required S3 objects.
            - Permanent IAM user access keys are not stored on the server.


    # Service Roles:
        An AWS service may need permission to perform actions on your behalf.

        A service role is an IAM Role used by an AWS service.

        Examples:
            - EC2
            - Lambda
            - Other AWS services

        Example:
            A Lambda function needs to write logs.

        Solution:
            - Attach an execution role with the required permissions.
            - Lambda assumes the role.
            - Temporary credentials are used automatically.


    # Cross-Account Access:
        IAM Roles can also provide access between AWS accounts.

        Example:

            Account A
                --> User or Role

            Account B
                --> IAM Role

        Account B can create a role that trusts an identity from Account A.

        The authorized identity from Account A can then assume the role
        and temporarily receive the permissions defined in Account B.


    # Cross-Account Flow:
        Account A User / Role
            --> Assume Role in Account B
            --> Receive Temporary Credentials
            --> Access Allowed Resources in Account B

        Benefit:
            - No need to create permanent IAM users in every AWS account.


    # Role Session:
        When a role is assumed, AWS creates a role session.

        During the session:
            - Temporary credentials are active.
            - The role's permissions are used.
            - The credentials expire when the session ends.

        A new role session requires new temporary credentials.


    # Why Temporary Credentials are Safer:
        Temporary credentials reduce the risk of exposed credentials.

        If temporary credentials are exposed:
            - They have a limited lifetime.
            - They stop working after expiration.

        Long-term credentials:
            - May continue working until manually disabled or deleted.

        Therefore:
            - Prefer temporary credentials whenever the AWS use case supports them.


    # Avoid Hardcoding Access Keys:
        Do not place long-term AWS access keys directly inside:

            - Application source code
            - Scripts
            - Git repositories
            - Public configuration files

        Better approach:
            - Use IAM Roles and temporary credentials.


    # Least Privilege with Roles:
        A role should receive only the permissions required for its task.

        Example:
            EC2 application only needs to read one S3 bucket.

        Better:
            - Allow required read actions.
            - Limit access to the required bucket.

        Avoid:
            - Administrator access.
            - Full S3 access when only read access is required.


    # Common IAM Role Use Cases:
        1. EC2 accessing S3
            --> EC2 assumes a role.

        2. Lambda accessing DynamoDB or other AWS services
            --> Lambda uses an execution role.

        3. Cross-account administration
            --> User assumes a role in another AWS account.

        4. Federated users
            --> Users receive temporary AWS access through a role.

        5. Applications requiring AWS permissions
            --> Use temporary credentials instead of embedded long-term keys.


    # Simple Security Rule:
        If an AWS service or application needs AWS permissions:

            First Ask:
                "Can I use an IAM Role?"

        If yes:
            --> Prefer the IAM Role.

        Avoid creating long-term access keys unless they are genuinely required.


    # Quick Summary:
        1. IAM Role
            --> AWS identity with permissions that can be assumed.

        2. Temporary Credentials
            --> Short-term credentials that expire automatically.

        3. Temporary Credential Components
            --> Access Key ID + Secret Access Key + Session Token.

        4. AWS STS
            --> Service that provides temporary security credentials.

        5. AssumeRole
            --> Used to obtain temporary credentials for a role.

        6. Trust Policy
            --> Defines who can assume the role.

        7. Permissions Policy
            --> Defines what the role can do.

        8. EC2 Role
            --> Lets applications on EC2 access AWS without hardcoded keys.

        9. Service Role
            --> Lets an AWS service perform permitted actions.

        10. Cross-Account Role
            --> Provides temporary access between AWS accounts.

        11. Least Privilege
            --> Give the role only the permissions it needs.

        12. Best Practice
            --> Prefer temporary credentials over long-term access keys.


    # Lecture Summary:
        "IAM Roles provide permissions without requiring permanent credentials.
        When a user, application, or AWS service assumes a role, AWS STS provides
        temporary credentials for a limited session. Trust policies control who
        can assume a role, permissions policies control what the role can do,
        and roles should follow the principle of least privilege."
